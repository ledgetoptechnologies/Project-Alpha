# Future contacts beneath completed portal roots

The configured automatic portal producer already provisions future clients through normal PA mutation hooks and discovers new roots through its background reconciliation. A neutral API directory create intentionally does neither. The completed-root marker previously prevented background reconciliation from discovering a later neutral contact beneath an existing company.

Background reconciliation now spends the remaining per-run budget on missing contacts beneath a completed, same-contract organization root. It requires the same ready unique producer, an active root, active workspace and active producer/workspace link, active client and company, no eligibility row, and no protected contact-identity policy row. It locks and rechecks these witnesses before reconciling exactly that client. Existing eligibility, protected NONE, manual revocations, archived parents and inactive workspaces are never restored or replaced.

The publisher queues current portal authority without invoking root-wide provisioning or workspace lifecycle transitions. Other clients, principal associations, identity bindings, entitlements and completed-root markers remain unchanged. Generic API directory creation stays neutral. No new endpoint, API scope, migration or runtime environment setting is introduced.

The existing integration audit records bound failed attempts to five per client/producer contract, prioritize untried contacts, and preserve fixed error codes rather than exception data. A failed target does not reopen its root or block untried contacts. Terminal failures remain visible in reconciliation counts; explicit administrator repair/review remains necessary. Invalid/duplicate email becomes review-required without a principal, consistent with existing provisioning policy.

SQLite tests cover real own-binding proof and published principal, unchanged existing authority, exact cron/policy/root races, stale/protected/revoked/archived cases, malformed or duplicate email, projection rollback, failure exhaustion, new-root budgeting, replay and separate service/PDO isolation. Existing directory-create neutrality tests remain part of the focused suite. These are not a claim that live PA-to-Ops onboarding has completed.

The additional database test requires a fresh migrated disposable MySQL database with zero clients/profiles/principals, `PA_DISPOSABLE_SCHEMA_PROOF=1` and test-only `PA_PENDING_CLIENT_MYSQL_ALLOW=isolated-disposable-only`. It checks real MySQL locking/current reads, exact own binding proof/publication and a duplicate email committed on a second connection after the locked target read. The runner must destroy the disposable database afterward; never point this fixture at an application database. No live server, production or TrueNAS test is authorized by this document.
